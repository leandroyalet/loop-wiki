# Observability

**Observability** means being able to see, after the fact, what a loop did and why. No ingested source treats it as a topic in its own right. This page collects the scattered evidence. Up: [[control]].

## Evidence so far
- **Transparency principle:** *"explicitly showing the agent's planning steps"* ([[src-anthropic-building-effective-agents]]).
- **Explained scheduling:** a self-paced `/loop` prints its chosen delay *and the reason* each iteration ([[src-claude-code-scheduled-tasks]]).
- **The state file as an audit trail:** it records what was tried, what passed and what is open ([[src-osmani-loop-engineering]]). See [[context-and-state]].
- **Watching the stream:** Huntley watches Ralph's output live to find patterns worth tuning ([[src-huntley-ralph]]).
- **Inbox, not silence:** in Codex, runs that find something go to a triage inbox and empty runs archive themselves ([[src-osmani-loop-engineering]]).
- **An audited decision log:** pstack's `/show-me-your-work` appends one row per decision (time, phase, decision, reason, evidence pointer, result) to `decisions.tsv`. At the end it checks the log against the transcript, and a reviewer from a **different model family** writes an **Attention** section. *"You're auditing decisions, not re-reading the whole night"* ([[src-tan-pstack-guide-overnight]]).
- **A trail you can trust.** `/show-me-your-work`'s evidence column holds a pointer (SHA, PR, `file:line`, artifact path), *"never prose"*. A wrong call gets a superseding row instead of an edit: *"Correct the log, not the story"*. *"Self-review is not a substitute"* ([[src-inside-pstack-report]]).
- **Catch-ups, not reports.** pstack's autopilots end every tick that changed something with a `/ketchup`. It runs under 150 words, puts captured screenshots and videos first, ends with action items, and follows the rules *"Never make up a call to fill the reply"* and *"Never draw … a picture of a screen you did not capture"* ([[src-inside-pstack-report]]).
- **Typed status.** `watch-pr` reports a PR's state as an exit code (ready, conflicts, threads, failing checks, gate, timeout), so a babysitting loop reads a verdict rather than parsing a page ([[src-inside-pstack-report]]). See [[babysitter-loop]].
- **Audit by side effects.** An hourly `/loop` audit in Autopilot-full judges agents by what they changed, not by what they reported ([[src-inside-pstack-report]]).
- **A tool-call event stream (AgentOS).** Every tool call emits `started` / `completed` / `failed` events with latency, result or error, `session_id`, `client` and `working_dir`. Many subscribers can watch at once (CLI, browser SSE, debuggers). The live bus is lossy, and a slow viewer gets a `lagged` notice, but *"durability lives in the graph, not in the channel"* ([[src-agentos-docs]]).
- **Agent activity as queryable data.** `session` and `tool_call` are stored entities aligned with OpenTelemetry GenAI conventions, so you can ask for *"every tool call that errored."* Every change is an entity attributed to an actor, human or agent (W3C PROV-O) ([[src-agentos-docs]]). *(synthesis)* This is the first source in the wiki to point at a tracing standard for agent loops.
- **Evidence artifacts:** screenshots, videos, traces and heap snapshots posted by each stage. *"Artifacts … beat a plausible sounding explanation"* ([[src-tan-loops-you-can-trust]]).
- **Slack as a control room:** thread markers and status updates show the state of the whole line ([[src-tan-loops-you-can-trust]]).
- **Read thinking blocks** while you're in the loop to find failure modes worth encoding ([[src-tan-loops-you-can-trust]]).
- **Live streaming for AFK runs:** `--print` gives *"a blank screen"*. `--output-format stream-json` piped through `grep '^{' | tee | jq` streams assistant text live and keeps the final result for checking the sigil ([[src-pocock-afk-ralph-streaming]]).
- **Completion notification:** Pocock built a small CLI that pings him on WhatsApp when Ralph finishes, so he can *"fully engage with another task"* ([[src-pocock-ralph-tips]]).
- **The progress file and commits as a log:** each iteration appends decisions, blockers and files changed, and commits once per feature ([[src-pocock-ralph-tips]]).
- **Label AI output:** triage comments start *"This was generated by AI during triage"* ([[src-pocock-triage-skill]]).
- **Inspectable task lists:** `CronList` shows each scheduled task's ID, schedule and prompt ([[src-claude-code-scheduled-tasks]]).
- **A receipt per wake.** OpenProse signs a receipt for every wake (`rendered`, `skipped` or `failed`) into an append-only ledger. Each receipt carries fingerprints and a `cost` field (`provider`, `model`, `tokens: {fresh, reused}`, `surprise_cause`). `prose status` reads the active topology, trigger plan and recent receipts without running anything ([[src-openprose]]).
- **Reviewer transcripts as artifacts.** Every omp advisor turn is appended to `__advisor*.jsonl` inside the session folder. `omp stats` attributes its cost there, and Agent Hub shows it as a read-only transcript ([[src-omp]]).
- **An audit table for every outside write.** robomp records each host-tool call, with credentials redacted, in a `tool_calls` table. It also has a localhost dashboard and `/events`, `/issues` and `/releases` endpoints ([[src-omp]]).
- **A drift score as a monitored signal.** Ouroboros computes drift from the original Seed (goal 50%, constraints 30%, ontology 20%). Above 0.3 it triggers consensus review. Every event lands in a SQLite EventStore, and `ouroboros monitor` shows live progress. *"Low drift does not mean the feature is correct"* ([[src-ouroboros]]).

- **Human-effort metrics with a quality guardrail.** The Claude Code team tracks median and p95 human approvals per PR, human comments, and how long a PR waits on a person, with revert and incident rates as the guardrail. For the reviewer it tracks cycles-to-pass alongside recall, and classifies every review comment by how the author handled it: fixed, rejected, clarified as intentional, or didn't matter ([[src-osmani-claude-code-code-review]]). *(synthesis)* This is the first source in the wiki with a named metric set for a loop in production.
- **Incident reviews per layer.** Each incident review asks which layer should have caught the problem ([[src-osmani-claude-code-code-review]]). See [[rollback-and-recovery]].

## Contradictions & open questions
- Still wanted: sources on tracing, metrics and cost dashboards for agent loops. Everything above is practitioner tactics. The decision log and AgentOS's event bus are the most systematic so far. AgentOS records `tokenCount` per session but describes no cost dashboard ([[src-agentos-docs]]). The **OpenTelemetry GenAI semantic conventions** it cites are the obvious next source. See [[open-questions]].
